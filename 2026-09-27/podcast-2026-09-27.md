Maya: That frames the week less as “look, a new chatbot” and more as “what can builders do with a model they can run and shape?” The examples are striking, though they are experiments, not independent product reviews.
Alex: And they all lean on a different kind of model behavior. Jev returns choices or scores rather than composing a long answer. So the interesting question is: what changes when a model becomes a fast decision step inside a tool?
Maya: Moritz Kremb’s examples range from tiny conveniences to real-world actions. I’d start with the less dramatic ones, because they show how this could slip into ordinary software without announcing itself as AI.

Alex: One is a predictive launcher. Instead of matching only the letters you type, it ranks possible apps or actions using aliases and fuzzy matches. The model acts like a quick oracle for “what did you mean to open?”
Maya: That could make a launcher feel more forgiving, especially when you remember what something does but not its exact name. But speed alone isn’t enough: the top result has to be predictable, and a wrong launch should be easy to correct.
Alex: The more surprising idea is “instant compaction.” Today, when an agent’s conversation gets too long, it often asks a language model to summarize the history. Moritz suggests scoring tool calls and dropping the ones that no longer matter.
Maya: So rather than rewriting the whole past into a shorter story, the system would keep the useful events and discard the rest. I like the distinction. But deciding what matters later is the hard part: a seemingly minor call can explain a later failure.
Alex: Right. It sounds a bit like keeping the useful receipts instead of asking someone to write a memoir of every shopping trip. If the scoring is good, it could save time and context; if it misses a key detail, the agent may lose its bearings.
Maya: And we don’t yet have a result in the post showing how well that works over long tasks. “Instant” describes the proposed mechanism, not proof that the compressed history preserves everything a later step will need.

Alex: There’s also a PostgreSQL extension idea: call `jev(people, 'could work from home')` or even ask whether a name sounds European. The post says it judged 129 rows in about one second, without an index or embeddings.
Maya: That’s a compact demo, but the second query hints at a risk as well as a feature. “Could work from home” might be an inference from several columns; “sounds European” could invite a fuzzy, biased guess about a person.
Alex: What is actually happening is that a natural-language question is being turned into a decision about which rows fit. That could spare an application team from building a separate search pipeline for every new question.
Maya: But “no index, no embeddings” doesn’t mean there’s no cost or engineering underneath. We’d want to know what the function evaluates, how results change with different wording, and whether the answer stays reliable on much larger tables.
Alex: Still, there’s a neat product possibility: a database query that feels flexible without asking the developer to set up a vector store first. The 129-row result is a proof of concept, not a scale test—but a useful one.

Maya: The browser examples move from searching to acting. In one, a person speaks, the transcript goes to Jev, it returns probabilities in roughly 300 milliseconds, and the browser clicks. The author says each decision costs about two-hundredths of a cent.
Alex: That latency matters because a spoken command feels broken if the page waits around for a paragraph of reasoning. And the post says it even handled “go back.” It’s a clever use of probabilities as a direct control signal.
Maya: But a 300-millisecond decision is only part of the experience. The browser still has to understand what is on screen, choose the right action, and recover if the page changes or the command is ambiguous.
Alex: A related flight-search demo reportedly found flights in seven seconds for about $0.0039. Its setup creates a new action space at each step, uses the page’s DOM state, and falls back to a small language model for typing.
Maya: That’s more informative than just saying “the browser agent is fast.” The DOM—the page’s structured elements—gives the system a current set of things it can act on. A fallback model can handle the text entry that doesn’t fit the fast decision step.
Alex: And the video was said to be at normal speed, not accelerated. If those times hold up across more than a demo, a low-cost decision model could make browser agents feel much less sluggish.
Maya: I’d still want to see the awkward cases: flights with changing prices, pop-ups, a slow page, or a result that looks plausible but violates the traveler’s constraints. Seven seconds is impressive only if it found the right trip.
Alex: That’s a fair qualification. I was about to read the speed as the main result, but for a booking task the useful result is a correct choice under changing conditions—not merely a quick sequence of clicks.

Maya: The experiments also reach into financial actions. Moritz says he built a trading bot where Jev chooses “buy” or “sell” from an asset-pair price feed, then places real trades on Monad through Kuru’s on-chain order book.
Alex: The orders happen in every 300-millisecond block, according to the post. That’s a striking demonstration of low-latency control: the model is not drafting advice for a human; it is connected to a mechanism that can move money.
Maya: And that changes the standard of evidence. A demo that clicks the wrong browser button is annoying. A trading system can lose money, and a fast loop can repeat a bad decision before a person has time to intervene.
Alex: We should be precise: the post establishes that a bot was built and shown, not that its strategy made money or managed risk well. A buy-or-sell output is not, by itself, a trading edge.
Maya: Exactly. I’d want limits on order size, a way to stop it, and careful testing against fees and price swings. The technical trick is interesting, but the operational guardrails are part of the product, not an optional extra.

Alex: That connects to another experiment that is less about a single decision and more about the whole machine. Moritz describes TypeGPU and ruNNtime running local inference alongside graphics, with zero-copy sharing of GPU resources.
Maya: He says three separate neural-network inferences and rendering run in real time. “Zero copy” means data can be shared without repeatedly moving it between parts of the system—a transfer that can add delay and use resources.
Alex: So the pitch is not just “this model is quick.” It’s that inference and rendering can share the graphics processor efficiently, potentially making richer local applications practical. That’s a real systems idea, not only a model benchmark.
Maya: Though we don’t get enough detail here to judge which workloads benefit, or what hardware was used. Three inferences in real time is a useful claim to investigate, not yet a promise that any laptop can do it.

Alex: Which brings us back to Gautham’s point about open weights. If builders can inspect or run the model themselves, these ideas are easier to test, adapt, and potentially host closer to the user or the data.
Maya: That’s a meaningful advantage, but it doesn’t settle the business case. Open weights are a differentiator only if the model is useful, the license permits the intended use, and the surrounding tools are good enough to build on.
Alex: I also wouldn’t treat all these demos as evidence for one broad capability. A launcher, database filter, voice command, flight search, and trading decision ask different things of the system.
Maya: Yes. The common thread is narrower: quick, bounded choices can be woven into workflows, sometimes with a larger language model handling the parts that need more flexible text or reasoning.
Alex: And the real test is whether that division of labor survives contact with messy inputs. The demos make the idea tangible; they don’t yet tell us where the fast decision step should hand off, or when it should refuse to act.

Maya: Maybe the image to leave with is that trading loop, making a decision every 300 milliseconds. The unresolved question isn’t only whether Jev can choose quickly—it’s how quickly a bad choice can compound before anyone notices.
